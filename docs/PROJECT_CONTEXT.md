## 3. プロジェクトの目的とプロダクト構想

### 3.1 現時点の目的

`[確定]` ハッカソン最終日に動作するアプリを提示し、説明用スライドを使って発表する。

`[確定]` 採用案は、シチュエーションに対する判断を通じて知識や理解度を確認するゲームである。アプリ全体をモラル編と男心編に分ける。

`[確定]` モラル編では、社会人によるSNS投稿や情報の取り扱いが問題になる事例を背景に、学生・新卒が実務に入る前に知っておきたい社会人の常識・マナー・リテラシーを題材とする。堅い研修ではなく、遊び心のある体験を通じて楽しく学び、判断を振り返れることを目指す。

`[確定]` 対象ユーザーの年齢層は20代前半〜後半である。

`[暫定]` 企業の内定者ハッカソンとして内定者を主な利用者に想定するが、内定者専用には限定しない。アプリ名は「空気読メーター」に決定したが、各編の正式名称とキャッチコピーは決まっていない。

`[現状実装]` この作業ブランチでは、診断結果をAIとのコミュニケーションに生かせる作業用プロフィールへ変換し、OKFのConcept文書として扱えるYAMLフロントマター付きMarkdownを1ファイルでダウンロードできる。AI向けの会話配慮、本人へ確認すべき未確定事項、断定・推測してはいけない事項を先に記載し、点数や相性候補は根拠を確認するための参考資料として後半へ分離する。出力はブラウザ内だけで生成し、匿名ID、回答の生ログ、不要な個人情報は含めない。

次の項目はまだ明文化されていない。

- `[未決定]` 男心編で具体的に何を測り、どのような学びや楽しさを提供するか
- `[未決定]` モラル編と男心編を合わせたプロダクト全体の価値をどのように説明するか
- `[未決定]` ハッカソンでの成功条件・評価指標
- `[未決定]` モラル編・男心編の正式名称と、アプリ全体のキャッチコピー

### 3.2 体験フローの現在地

1. `[現状実装]` トップ画面でモラル編または男心編を選び、スタートする。
2. `[現状実装]` モラル編ではテーマ、男心編では担当者を選ぶ。
3. `[現状実装]` 個別ページでシチュエーションと問題を提示する。
4. `[現状実装]` プレイヤーが画面上の選択肢などで回答する。回答形式や問題数は担当ページごとに異なる。
5. `[現状実装]` 各担当ページの採点結果を、モラル編は5評価軸を含むテーマ結果、男心編はメンバー別の一致度として共通Storeへ保存する。
6. `[現状実装]` 各編の集計画面と総合診断結果画面を表示する。総合画面ではモラル点と男心編の一致度を平均せず、両編を分けて説明する。
7. `[現状実装]` 1件以上の完了結果があれば、AI向けの会話配慮と診断根拠を分離したコミュニケーションプロフィールを、YAMLフロントマター付きMarkdownの1ファイルとしてダウンロードできる。
8. `[未決定]` 別テーマへの移動、再挑戦、結果共有などの終了後の導線を決める。

この作業ブランチでは手順1〜7を実装している。総合診断は完了済みの結果だけを使い、モラル編5テーマかつ男心編5人の完了で「完了」、それ以外は「途中診断」とする。0件完了時は空状態を表示し、ダウンロードを無効にする。

## 7. 技術方針の現在地

- `[確定]` 初心者が多いチームであることを踏まえ、HTML5、CSS、Vanilla JavaScriptを基本構成とする。
- `[確定]` 技術的な複雑さより、UI、画面構成、ゲーム進行、回答体験を工夫する。
- `[確定]` 担当者は原則として自分のフォルダ内のHTML、CSS、JavaScriptだけを編集し、競合を避ける。
- `[現状実装]` 実行時の外部ライブラリやフレームワークはない。開発時の静的確認用に`package.json`とdevDependenciesがあるが、アプリ本体は静的HTML、CSS、Vanilla JavaScriptだけで動作する。
- `[現状実装]` バックエンド、DB、認証、外部API接続はない。
- `[現状実装]` GitHub Actionsから静的ファイルをGitHub Pagesへ公開する設定がある。
- `[現状実装]` モラル編と男心編はそれぞれ共通Storeへ結果を保存し、編別集計と総合診断結果から参照できる。総合診断では尺度の異なる両編を単純平均しない。
- `[暫定]` MVPはフロントエンドだけで完結させる。バックエンド等が必要になった場合はチーム確認を行う。
- `[現状実装]` 診断結果は、AIが会話で参考にできる仮説、本人へ確認すべき事項、推論上の制約、診断根拠をまとめたOKF互換のYAMLフロントマター付きMarkdown 1ファイルとしてブラウザ内で生成できる。ファイル生成時の外部送信は行わず、AIへの共有は利用者自身の操作とする。
- `[暫定]` CSSアニメーションで画面パーツ・ページ遷移に動きを付ける案がある。ただし本番期間に時間の余裕がある場合の追加候補で、実装範囲と担当は未確定である。
- `[未決定]` LLMを採点、設問生成、結果コメント生成のいずれかに使うか。現在のMVPには導入されていない。
- `[現状実装]` 状態と集計結果はブラウザのlocalStorageへ保存する。匿名IDや回答の生ログはOKF出力に含めない。

AIは、技術選定が済んでいると仮定してフレームワークや依存関係を追加してはならない。新しい依存関係、API、DB、認証を提案・導入する場合は、目的、MVPへの必要性、開発時間への影響を示してチームの確認を取る。

同じ事項について記述が矛盾する場合は、最新のユーザー確認、ミーティング資料、Slackキャンバスを、旧スプレッドシートの記述より優先する。タスクの実際の状態はGitHub Projects、実装の実際の状態はリポジトリ内のコードを優先する。

### Git運用

READMEでは次の流れを推奨している。

1. 作業前に `main` の最新状態を取得する。
2. `main` に直接コミットせず、作業用ブランチを作る。
3. 担当者ごとのフォルダが用意されているため、原則として自分のフォルダ内の3ファイルだけを変更する。
4. 変更対象と差分を確認してからコミットし、作業ブランチをリモートへpushする。
5. Pull Requestを作り、レビュー後に `main` へマージする。

mainの内容を作業ブランチへ取り込む操作はmain本体を変更しない。mainが変更されるのは、mainへ直接pushするか、Pull Requestをmainへマージした場合である。

コミット、push、Pull Request作成、mainへのマージは、対象、内容、影響を担当者が確認したうえで別々に行う。

## 13. AIが作業するときのルール

1. まずこの文書と、変更対象の実ファイルを読む。
2. 実装タスクの担当・期限・優先度は GitHub Projects を確認する。
3. `[暫定]`、`[未決定]`、`[推定]` の内容を、チーム承認済みの仕様として扱わない。
4. 「計画されている機能」と「現状実装」を明確に分けて説明する。
5. 対象ユーザー、仕様、技術構成を推測だけで確定しない。
6. 新しい依存関係、バックエンド、DB、外部API、認証を無断で追加しない。
7. 既存の命名、構成、コードスタイルを優先し、必要最小限の差分にする。
8. 日付、参加可否、`△` の意味など、資料内で曖昧な情報を勝手に補完しない。
9. プロジェクトの決定が更新されたら、正本を先に更新し、その後この文書へ反映する。
10. 現在のチーム判断と会議予定について旧スプレッドシート、ミーティング資料、Slackキャンバスが矛盾する場合は、最新のユーザー確認と資料を優先する。
11. mainの画面案・デザインと現在のフォルダ構成を公式の基盤として扱う。
12. 個別問題の実装では、原則として担当フォルダ内のHTML、CSS、JavaScriptだけを変更する。共通画面や他担当のファイルを変更する場合は先に調整する。
13. 画面上に説明文があっても、対応するJavaScript処理がない機能を実装済みとみなさない。
14. 診断結果や解説は学習と振り返りを目的とし、人格・適性・性別一般を断定する表現を避ける。
15. commit、push、Pull Request、mainへのマージを、まとめて暗黙に許可された操作として扱わない。
16. 加藤さんの参加・問題提供は、打診と本人の回答・掲載許可が確認できるまで確定事項として扱わない。
17. 結果ファイル出力は、OKF互換のYAMLフロントマター付きMarkdown 1ファイルをブラウザ内で生成する。診断結果を客観的な人格評価として扱わず、AI向けの配慮は会話開始時の仮説として記述する。現在の本人の希望を優先し、男心編の相性候補を本人のMBTI・Love Typeとして扱わない。匿名ID、回答の生ログ、不要な個人情報は含めない。
18. ミーティング資料の「出来次第」「29日頃」「時間の余裕がある場合」という表現を、完了済み、確定期限、確定担当と読み替えない。進捗はGitHub Projects、実装はリポジトリのコードで別途確認する。
