## 2. AI向け最短要約

- `[確定]` チームはハッカソンに向けて、アプリと最終発表スライドを制作する。
- `[暫定]` 最も具体化されている案は「モラルチェッカー・男心理解度ゲーム」。シチュエーションに対して選択肢で回答し、固定ルールで採点して点数を表示する構想が入力されている。
- `[重要]` 「プロジェクト概要」では採用案が「未決定」のままなのに対し、「アプリ案」では上記案に「（採用）」と記載され、「要件定義」でも同案の検討が進んでいる。正式採用済みかはチーム確認が必要。
- `[現状実装]` リポジトリにあるのは HTML/CSS/JavaScript の静的ランディングページ雛形だけで、ゲーム本体は未実装。
- `[未決定]` 対象ユーザー、設問内容、結果表示の詳細、技術構成、データ保存、ログイン、MVP範囲、担当分担、デモ構成は決まっていない。
- `[確定]` タスクと進捗の正本は GitHub Projects。プロジェクト計画・チーム情報の参照元は Google スプレッドシート。実装状況の正本はリポジトリ内のコード。
- AIは未決定事項を事実として補完せず、実装前に GitHub Projects とチームの最新判断を確認すること。

## 3. プロジェクトの目的とプロダクト構想

### 3.1 現時点の目的

`[確定]` ハッカソン最終日に動作するアプリを提示し、説明用スライドを使って発表する。

`[推定]` 現在最も具体化されているゲーム案は、日常的なシチュエーションへの回答を通じて、プレイヤーのモラル判断や男性心理への理解度をゲーム形式で可視化することを目指している。

次の項目はまだ明文化されていない。

- `[未決定]` 誰の、どのような課題を解決するか
- `[未決定]` 主な対象ユーザー
- `[未決定]` ユーザーに提供する価値
- `[未決定]` ハッカソンでの成功条件・評価指標
- `[未決定]` 正式なアプリ名とキャッチコピー

### 3.2 暫定的な体験フロー

以下は要件定義シートの記述から整理したもので、チーム承認済みの仕様ではない。

1. `[推定]` ゲームの説明を表示する。
2. `[暫定]` モラルまたは男性心理に関するシチュエーションと選択肢を表示する。
3. `[暫定]` プレイヤーが選択肢を選んで回答する。
4. `[暫定]` 回答を固定ルールで採点する。
5. `[暫定]` 合計点を表示する。
6. `[未決定]` 診断タイプ、解説、コメントなどの詳細結果を表示する。

## 7. 技術方針の現在地

- `[現状実装]` HTML5、CSS、Vanilla JavaScriptのみ。
- `[現状実装]` 外部ライブラリ、フレームワーク、パッケージ管理ファイルはない。
- `[現状実装]` バックエンド、DB、認証、外部API接続はない。
- `[未決定]` 現在の静的構成をMVPでも継続するか。
- `[未決定]` LLMを採点、設問生成、結果コメント生成のいずれかに使うか。

AIは、技術選定が済んでいると仮定してフレームワークや依存関係を追加してはならない。新しい依存関係、API、DB、認証を提案・導入する場合は、目的、MVPへの必要性、開発時間への影響を示してチームの確認を取る。

### Git運用

READMEでは次の流れを推奨している。

1. 作業前に `main` の最新状態を取得する。
2. `main` に直接コミットせず、作業用ブランチを作る。
3. 変更をコミットし、作業ブランチをリモートへpushする。
4. Pull Requestを作り、レビュー後に `main` へマージする。

コミット、push、ブランチ作成は、担当者が内容と影響を確認したうえで行う。

## 13. AIが作業するときのルール

1. まずこの文書と、変更対象の実ファイルを読む。
2. 実装タスクの担当・期限・優先度は GitHub Projects を確認する。
3. `[暫定]`、`[未決定]`、`[推定]` の内容を、チーム承認済みの仕様として扱わない。
4. 「計画されている機能」と「現状実装」を明確に分けて説明する。
5. 対象ユーザー、仕様、技術構成を推測だけで確定しない。
6. 新しい依存関係、バックエンド、DB、外部API、認証を無断で追加しない。
7. 既存の命名、構成、コードスタイルを優先し、必要最小限の差分にする。
8. 日付、参加可否、`△` の意味など、資料内で曖昧な情報を勝手に補完しない。
9. プロジェクトの決定が更新されたら、正本を先に更新し、その後この文書へ反映する。
